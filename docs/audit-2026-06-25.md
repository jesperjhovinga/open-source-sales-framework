# BD Automation Framework — Deep Audit

**Date:** 2026-06-25 · **Scope:** full repository · **Goal:** improve everything; make the framework genuinely portable (no person/company hardcoded outside the Org Context).

---

## Executive summary

The repo has a strong, well-articulated architecture on paper: a portable **BD Core** (ubiquitous language, context contract, path conventions) and a swappable **Org Context** (`contexts/<org>/`) that holds all person/company specifics, consumed through documented surfaces (`context.tone`, `context.icp`, …).

The problem is a **split between intent and implementation**:

1. **The skills were written ahead of the contract.** They hardcode "the BDOwner"/"ExampleOrg"/proposition names and read files by direct path instead of consuming context surfaces. The specs are contract-faithful; the skills are not. They don't match.
2. **The Org Context is mostly unbuilt.** Only 2 of 8 contracted surface files exist, and one of those is misnamed — so the contract would "fail loud" for half the specs that depend on it.
3. **The status docs are stale and contradict each other and reality** (skill counts, version numbers, "no skills implemented yet").
4. **Portability is asserted but never tested** — there is no second/blank Org Context, so the central architectural claim has never actually been exercised.

The headline for your stated goal: **personal/company references leak into the portable layer in 14 files** (105 occurrences in skills, plus 4 in Core). That includes the skills I added this session — they're part of the problem, not exempt from it.

The single highest-leverage move is to **make the skills consume the contract surfaces instead of hardcoding specifics and reading raw paths**, and to **build out `contexts/<org>/` + a blank template** so the contract resolves. Everything else is cleanup hanging off that.

## A. Portability leaks (your explicit ask)

Personal/company specifics belong only in `contexts/<org>/`, referenced by the `BDOwner` role and the context contract. They currently leak into the portable layer:

- **Core leaks** (worst, because Core is the portable foundation):
  - `core/language/glossary.md` — `BDOwner — the human (the human owner at the org)`; `Workshop`/`WorkshopParticipant` defined as "org-specific" motions. A person and a company go-to-market motion are baked into the shared vocabulary.
  - `core/context-contract.md` — names the org's propositions inline (`"example_prop_a"`/`"example_prop_b"`). Acceptable as illustration, but should be flagged as example.
- **Skill leaks** (105 hits across 12 files). Notable:
  - `bd-user-rules` — hardcodes the BDOwner/ExampleOrg/propositions, and **every BD skill inherits it**, so this one leak propagates framework-wide.
  - `bd-skill-evolution` — embeds live prospect examples ("ProspectCo isn't a customer of that client", "correct-name not wrong-name") into an always-active meta-skill.
  - `cold-call-prep` — full ExampleOrg pitch as prose ("Dutch digital product agency… derisk and accelerate…").
  - `event-invite` + `assets/signals-2026-example.md` — the most concentrated leak: real event details, `contact@example.com`, and real contact names (three real first names) living inside a skill asset.
  - `account-research`, `bd-email`, `call-notes-to-crm`, `prospect-sourcing` (NL-only disqualifiers hardcoded), and specs (`outreach-drafting`, `account-research`, `discovery-call-prep`) all hardcode names/paths/propositions.
- **Clean, for contrast:** `marketing-psychology`, `revops`, `sales-enablement`, `cold-email`, `email-sequence`, `grill-me`, `handoff` — zero org specifics. These show the target state.

**Honest note:** the six skills I built this session (`bd-email`, `event-invite`, `call-notes-to-crm`, `bd-skill-evolution`, `bd-user-rules`, `bd-skill-card`) are among the leakers. They read `contexts/<org>/` correctly in places but still say "the BDOwner" throughout. They need the same de-naming pass.

## Recommended refactor — prioritized

**P0 — fixes that unblock everything else and directly serve portability**
1. **Resolve the contract↔file mismatch.** Rename `tov.md` → `tone-of-voice.md` (or update the contract/path-conventions to `tov.md`). Pick one and make all skills consume `context.tone(channel)` instead of a raw path.
2. **De-name the portable layer.** Strip the BDOwner/ExampleOrg/proposition names from Core (`glossary.md` `BDOwner`, `Workshop`) and all skills; reference the `BDOwner` role and pull specifics from Org Context. Move `signals-2026-example.md` content into `contexts/<org>/`.
3. **Single voice source.** Delete the duplicated banned-word lists; have every voice skill inherit `context.tone`. (`bd-user-rules` already wants to be the inheritance point — make it reference the surface, not restate it.)

**P1 — make the contract real**
4. **Build `contexts/<org>/` surface files** (even as stubs): positioning, value-props, competitors (lift from `icp.md`), content-library, pricing, connectors. Tick the README checklist as they land.
5. **Add `contexts/_template/`** — a blank skeleton of every surface, so a new org is copy-and-fill. This is the portability proof.
6. **Canonicalize proposition IDs** to `example_prop_a`/`example_prop_b` everywhere.

**P2 — consistency, accuracy, hygiene**
7. **Reconcile status docs** — fix STATE.md (17 skills, 5 specs), rewrite the stale README, single source of version truth.
8. **Fix the SPICED bug** in `glossary.md`.
9. **Unify frontmatter** — one version scheme across all skills; decide on the spec↔skill↔test triad (either build the missing skills/specs/tests or drop the convention).
10. **Decide the plugin/eval-harness claims** — build `plugin.json` + `tests/` or remove the claims from docs so they stop lying.

**Deliberately deferred:** CRM auto-write (waiting on a connector), and full de-personalization of `contexts/<org>/` (it's correctly the example instance — keep it).

## Suggested sequencing

P0 is one focused pass (rename + de-name + dedupe voice) and delivers most of the portability win. P1 makes the contract resolvable and proves portability with the template. P2 is cleanup. I'd do P0 as a single reviewable diff, then P1, then P2 — rather than one giant rewrite, so each step is easy to check.

## G. Architectural review & efficiency (next layer — not yet done)

This audit is structural and portability-focused. A separate, deeper **architectural + efficiency review** is warranted. Early signals already visible, to investigate properly in that pass:

- **Token cost of duplication.** The voice/banned-word rules are restated in ~5 skills, so the same context is paid for on every invocation. A single inherited `context.tone(channel)` that returns *only* the relevant channel's rules (not the whole `tov.md`) cuts repeated context. Same logic for the proposition/positioning text.
- **Surface scoping vs. whole-file reads.** Skills currently read entire files (`icp.md`, `tov.md`). The contract's channel/segment-scoped surfaces (`context.tone("email_cold")`, `context.icp(segment)`) would load less and target better — but only once a resolver exists.
- **The missing resolver (Decision 9).** Every skill re-implements "find file → read → handle missing." A thin resolver/wrapper for surface calls removes that boilerplate, centralizes fail-loud behavior, and enables caching across a chain (notes → CallNote → email currently each re-load context independently).
- **Trigger efficiency.** Overlapping skills (3 email skills, grill-me/grill-with-docs, skill+spec pairs) cause mis-triggers and wasted disambiguation turns. Clear boundaries = fewer wrong activations.
- **Progressive disclosure.** Some SKILL.md bodies could move reference detail into `references/` so the always-loaded portion stays lean.
- **Composition reuse.** The skill chain re-derives shared context per step; a single context-load shared across a session would be cheaper and more consistent.

A dedicated architectural review would also step back from file-level fixes to the bigger questions: is direct-file-read the right v0.x runtime or is the resolver/wrapper now worth building; does the spec↔skill↔test triad earn its keep or should it collapse to skills-only; and what's the smallest core that still delivers the 80–90% automation goal in STATE.md.
